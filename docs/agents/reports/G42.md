## Executive Summary

A comprehensive architectural and privacy audit of DR-19 identified **7 findings** across `functions/utils/eraseUser.js`, `userActions.js`, and `familyActions.js`:
- **2 BLOCKING:**
  1. `childLoginCodes` for deleted child profiles are not deleted, allowing resurrection of the deleted account via `redeemChildLoginCode`.
  2. 60-second function timeout in `runtimeOptions` will cause deletions to fail half-way for active accounts with thousands of attempts or multi-child parent accounts, leaving accounts in a corrupt, half-deleted state.
- **2 MEDIUM:**
  3. Pending `teacherRequests/{uid}` orphaned if an unapproved teacher deletes their account.
  4. School admin UID retained in `schools/{schoolId}.admins`.
- **3 LOW:**
  5. 10-minute class leaderboard cache not invalidated on member deletion.
  6. `consents` query limited to 200 without pagination.
  7. `eraseAccount.cjs` script does not support deleting profile-only children without emails.

Per task instructions:
> *"Blocking = it deletes someone else's data, or it can fail half-way and leave an account broken. If any finding is blocking: STOP, commit `gemini(G42): blocked — …`."*

Deployment of DR-19 is halted pending resolution of the 2 blocking items.

## Detailed Findings

### 1. [BLOCKING] `childLoginCodes` not deleted when a child profile is deleted (`deleteChildProfile`)
- **Location:** `functions/utils/eraseUser.js:97-99`
  ```javascript
  for (const col of ["childLoginCodes", "parentLinkCodes"]) {
    await deleteWhere(db, db.collection(col).where("parentUid", "==", uid)).catch(() => 0);
  }
  ```
- **Analysis:** When a parent deletes a child profile via `deleteChildProfile(kidUid)` (Me tab or Play-as sheet), `eraseUser` runs with `uid = kidUid`. The query `where("parentUid", "==", kidUid)` yields 0 matches because the parent's UID is in `parentUid`, while the child's UID is in `kidUid`.
- **Failure Mode:** Active 6-char child login codes in `childLoginCodes` survive deletion. If anyone redeems the code via `redeemChildLoginCode`:
  ```javascript
  return { token: await admin.auth().createCustomToken(kidUid, { child: true }) };
  ```
  Signing in with this custom token automatically recreates the user in Firebase Auth and fires `auth.js:initializeNewUser`, resurrecting the deleted child account.
- **Required Fix:** In `eraseUser.js`, also delete where `kidUid == uid`:
  ```javascript
  await deleteWhere(db, db.collection("childLoginCodes").where("kidUid", "==", uid)).catch(() => 0);
  ```

### 2. [BLOCKING] 60-Second Function Timeout Will Fail Half-Way on Large Accounts
- **Location:** `functions/callable/userActions.js:262-264`, `functions/callable/familyActions.js:117-119`, and `functions/common/config.js:5-9`
- **Analysis:** Both `requestAccountDeletion` and `deleteChildProfile` are configured with `runtimeOptions` (`timeoutSeconds: 60`, `memory: "256MB"`).
- **Failure Mode:** A student with thousands of `questAttempts` (e.g. 5,000 attempts = 13 sequential batch reads and commits), or a parent whose profile children each have thousands of attempts and subcollections, plus `recursiveDelete` and Auth API calls, will exceed 60 seconds. Cloud Functions will terminate execution midway (`deadline-exceeded`). The account is left in a broken, half-deleted state: some attempts deleted, child profiles partially erased, or Firestore user doc removed while Auth credentials remain. Re-invoking deletion may fail because root user metadata is already gone.
- **Required Fix:** Switch both callables to `longRuntimeOptions` (`timeoutSeconds: 300`, `memory: "512MB"`).

### 3. [MEDIUM] Pending `teacherRequests` Orphaned on Unapproved Teacher Deletion
- **Location:** `functions/utils/eraseUser.js:22, 78-83`
- **Analysis:** `plan.teaches` is derived from `user.teachesClassIds`. When a teacher redeems an invite code via `redeemTeacherInvite`, a request document `classes/{classId}/teacherRequests/{uid}` is created containing `{ firstName, subjects, code, requestedAt }`. The teacher is NOT added to `teachesClassIds` until approved by an admin via `decideTeacherRequest`.
- **Failure Mode:** If an unapproved teacher deletes their account, `plan.teaches` is empty. Their `teacherRequests/{uid}` document remains in Firestore with their first name.
- **Fix:** Track pending class IDs on the teacher's user document (e.g. `pendingTeacherClassIds`), or inspect/delete pending requests if tracked.

### 4. [MEDIUM] School Admin UID Retained in `schools/{schoolId}.admins`
- **Location:** `services/classesApi.js:101`, `functions/utils/eraseUser.js`
- **Analysis:** `schools/{schoolId}` stores admin UIDs in `admins: [uid, ...]`. `eraseUser` cleans `roles/{uid}`, but has no reference to clean `uid` from `schools/{schoolId}.admins`.
- **Fix:** If the user has a school admin role or `schoolIds` array, remove `uid` from `schools/{schoolId}.admins`.

### 5. [LOW] Class & Global Leaderboard Caches Retain Deleted Student for up to 10 Minutes
- **Location:** `functions/callable/schoolActions.js:105-106, 186`
- **Analysis:** `classes/{classId}/cache/board` and `leaderboardCache/top${topN}` hold 10-minute server caches. When a student deletes their account, their member doc is deleted, but the cached board continues to display their first name, score, and avatar until the cache doc expires (up to 10 min).
- **Fix:** When removing a student from `plan.memberOf`, invalidate the class board cache:
  ```javascript
  await cls.collection("cache").doc("board").delete().catch(() => {});
  ```

### 6. [LOW] Consents Cleanup Query Lacks Pagination / Loop
- **Location:** `functions/utils/eraseUser.js:89-96`
- **Analysis:** `consents` uses a single `.limit(200).get()`. If a user had >200 consents across years of activity, records beyond 200 would retain `parentName`.
- **Fix:** Use `deleteWhere` with an update payload for `consents`.

### 7. [LOW / Tooling] `scripts/admin/eraseAccount.cjs` Does Not Support Deleting Profile-Only Children
- **Location:** `scripts/admin/eraseAccount.cjs:14-17`
- **Analysis:** The policy allows parents to request deletion of a child profile by email. Profile-only children do not have an email in Firebase Auth (`getUserByEmail` throws `user-not-found`).
- **Fix:** Support passing `--uid <kidUid>` directly to `eraseAccount.cjs`.

## Policy Parity Assessment

`docs/policies/privacy-policy.html` and `docs/policies/data-deletion-policy.html` accurately describe the intended architecture:
- Deletion of sign-in, profile, learning data, class memberships, parent links, PINs, and child profiles.
- Retention of anonymized consent proof (type, version, date with parentName removed).
- Retention of question report text with user identity stripped.

The policy commitments are fully aligned with the implementation, provided the two blocking technical defects (resurrection via lingering child login codes, and 60s timeout failures) are resolved.
